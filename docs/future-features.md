# Future Features

本文档记录 Video Skill Gather 在 v0.1 之后的候选功能、演进方向和立项约束。
它是产品路线候选清单，不代表所有功能都属于下一版本承诺。

## 1. 当前基线

v0.1 已跑通单个 B 站公开视频的主链路：媒体采集、抽帧、本地 faster-whisper
ASR、远程视觉/OCR、EvidenceTimeline、RIA++ Skill 草案、规则评分、LLM Judge
和候选包/失败审计包。

已有验证记录表明：

- 4 个公开 B 站样本中 3 个完成下载，成功样本共生成 80 帧、298 段 ASR 和 304 条证据。
- 3 次带密钥端到端运行中，2 次完成蒸馏，1 次因 `invalid_distillation_json` 失败；保存时间线后重试仍失败。
- 两个样本的规则分为 90，但标准 Judge 分别给出 18 和 32，说明评分校准和人工复核仍是主要问题。
- 视觉阶段在 18 帧和 35 帧样本中分别耗时 236.373 秒和 966.934 秒。
- `video` 在最终状态为 `failed` 时仍返回进程退出码 0，批处理前必须修复失败语义。

详细数据见 [`docs/mvp-validation-2026-07-30.md`](mvp-validation-2026-07-30.md)。

## 3. 可靠性与质量评测闭环

### 目标

让系统能够可靠地回答三个问题：

1. 这次运行为什么失败？
2. 生成的 Skill 是否真的有用？
3. 下一次重跑能否避免重复工作？

### 候选能力

- 蒸馏 JSON 解析失败时进行有限次数的结构修复或重试。
- 保存脱敏后的原始模型响应、解析错误和重试记录。
- 让最终失败状态返回非零进程退出码。
- 将规则评分、Judge 评分和人工复核结果分开记录。
- 建立固定视频基准集和人工标注准则。
- 输出通过率、拒绝率、需修改率、误拒绝和误通过等评测结果。
- 允许人工复核结果回流，作为后续 Judge 提示词和阈值校准依据。

### 关键约束

多个 Judge 不应简单平均分数。每个 Judge 应负责独立维度，例如可执行性、证据质量、
迁移性、边界和安全性。低成本筛选可以拒绝明显无效输入，但“不确定”必须进入后续阶段，
避免级联硬拒绝造成不可恢复的误杀。

### 验证方式

固定一组公开视频，预先定义人工判定标准，并报告规则 Judge、LLM Judge 与人工结论的
混淆矩阵。没有基准数据前，不预先承诺某个准确率百分比。

## 4. 分层 Judge 与低成本初筛

### 目标

在昂贵的抽帧、视觉理解和蒸馏前，筛掉明显不适合生成 Skill 的视频。

### 建议管线

```text
来源与访问检查
  -> 标题/简介/时长/分区初筛
  -> ASR 前段与画面信息密度检查
  -> 证据提取
  -> 可执行性 Judge
  -> 迁移性、边界和风险 Judge
  -> 综合状态
```

标题 Judge 只能作为低成本路由，不能单独判断 Skill 是否值得生成。标题可能缺少技术
细节，也可能与实际内容不一致。初筛状态应至少包括 `reject`、`continue` 和 `uncertain`。

### 验收重点

- 统计初筛节省的视觉调用数和墙钟时间。
- 单独统计误拒绝，不能只统计最终通过率。
- 保存每一层的输入、判断、理由和版本，保证可复核。

## 5. ASR 驱动的自适应截图

### 目标

根据口播中的知识点、动作和命令，决定何时采集画面，减少无信息帧和重复视觉调用。

### 建议流程

```text
ASR 分句
  -> 识别知识点/动作/命令
  -> 生成候选时间点
  -> 在时间点前后建立捕获窗口
  -> 场景变化、画面差异和 OCR 密度筛选
  -> 送高价值帧给视觉模型
```

候选时间点不应被当作唯一精确截图时间。口播和画面可能存在延迟，因此应保留前后时间窗，
并记录 `anchor_time`、`capture_window`、选择理由和置信度。

### 安全兜底

- 保留低频周期采样，防止 LLM 漏掉关键知识点。
- 对检测到代码、命令、配置、窗口切换的片段提高采样密度。
- 对前后帧相似且 OCR 密度低的画面降权或剔除。

### 验收重点

在同一冻结视频集上比较全帧方案和自适应方案的视觉调用数、墙钟时间、OCR/命令正确率
和漏证据数量。不能直接采用第三方项目宣传的加速比例作为本项目结果。

## 6. 本地 OCR 与帧筛选

### 目标

将简单文字识别、代码/命令候选检测和重复帧过滤尽量放在本地，减少远程视觉调用。

### 候选能力

- 接入本地 OCR 后端作为可选能力，不替换现有远程视觉主链路。
- 输出文字区域、置信度、坐标和候选类型。
- 用 OCR 密度、场景变化和帧相似度进行帧排序。
- 对高置信代码和命令帧优先送视觉模型。
- 将本地 OCR 和远程视觉结果合并进 EvidenceTimeline，并保留来源通道。

### 风险

本地 OCR 项目通常对文档和静态图像优化，不能假设在教程视频帧上必然更准或更快。
第一阶段只能做 A/B 实验，未达到项目内门槛时保留现有方案。

## 7. 小规模批处理

### 目标

将一个 URL 的处理能力扩展为一组已知 URL 的可恢复任务集合，验证“初筛 -> 提取 -> 再筛选”
是否有实际收益。

### 建议范围

- 输入一个 URL 文件或结构化清单。
- 先顺序执行小批量，默认不承诺并发。
- 每个视频保持独立 `VideoRun` 和独立审计包。
- 增加 `BatchRun` 作为父任务，记录汇总状态、预算和停止原因。
- 支持失败隔离、单项重试、取消和最终汇总。
- 增加最大视频数、最大帧数、最大视觉调用数和最大运行时间。

### 必要数据模型变化

当前 `RunState` 以单个 `source_id` 为中心。批处理需要父子任务关系、批次预算、子任务状态、
批次汇总和幂等重跑语义，不能只在 CLI 外层循环调用单视频命令。

### 不应提前承诺

在单任务失败语义、缓存和预算控制修复前，不上线无上限并发批量。

## 8. 跨视频证据合并与 Skill 去重

### 目标

从多个视频提取一个更可靠的 Skill，而不是简单拼接多个候选包。

### 候选能力

- 对相似候选 Skill 聚类和去重。
- 标记多来源一致支持、单来源观点和来源冲突。
- 按证据质量、来源独立性和时间戳完整度给证据加权。
- 在 Skill 中保留多个来源和时间片引用。
- 对冲突结论要求人工复核或生成明确的适用边界。

### 前置条件

- 稳定的 EvidenceTimeline 契约。
- 可区分来源和证据通道的 metadata。
- 可复现的人工复核标签。
- 批处理父子任务和成本预算。

## 9. 来源扩展：YouTube

### 目标

在不绕过访问控制的前提下，增加单个公开 YouTube 视频的来源适配。

### 范围

- 新增来源识别和 YouTube adapter。
- 沿用公开视频、无 cookie、无付费、无验证码和无地区限制的边界。
- 复用已有 EvidenceTimeline、RunState、评分和打包接口。
- 为来源特有的字幕、章节、媒体失败和访问限制增加风险标记。

### 风险

底层下载器支持某个平台不等于本项目能处理所有链接。必须使用真实公开样本验证，不能把
第三方支持站点清单写成成功率承诺。

## 10. 自动搜索到 Skill 生成

### 目标

根据用户主题自动发现视频，筛选后提取证据并生成可追溯 Skill，使 Search 和 Generate
形成闭环。

### 建议分阶段

1. 先支持用户提供的 URL 清单。
2. 再支持固定搜索源和有限结果数。
3. 增加候选去重、主题相关性排序和质量预测。
4. 最后做跨视频证据合并和 Skill 生成。

### 需要新增的能力

- 搜索查询生成和搜索结果规范化。
- 视频候选排序、去重和来源质量评分。
- 搜索缓存、刷新策略和预算控制。
- 任务队列、限速、失败隔离和停止条件。
- 跨来源证据引用、冲突处理和 Skill 去重。

### 立项判断

这是产品形态级扩展，建议作为 v0.3 及之后的方向。v0.2 先用小规模批处理验证经济性和
质量收益，不直接承诺开放式搜索。

## 11. 视频证据检索与多视频问答

### 目标

允许用户按主题或问题召回视频时间片，并返回带来源和时间戳的证据，而不是只生成静态 Skill。

### 候选能力

- 对 EvidenceTimeline 建立可检索索引。
- 支持关键词、语义和视觉类型过滤。
- 返回视频、时间点、证据通道和置信度。
- 支持跨视频比较和冲突提示。
- 将检索结果作为 Skill 蒸馏的输入。

### 立项判断

这会引入索引、召回评估、跨视频上下文和新的交互模型，属于很大扩展。应在批处理和
EvidenceTimeline 稳定后作为 v0.3+ 研究方向，不作为 v0.2 的交付承诺。

## 12. 本地 ASR 模型与参数基准

### 目标

在准确率、速度、显存和语言覆盖之间选择适合本项目的 ASR 配置。

### 候选能力

- 比较不同 faster-whisper 模型、设备和计算类型。
- 测量 VAD、批量转写和长视频分段的收益。
- 将模型配置、运行时间和资源占用写入 run metadata。
- 保留默认配置和可选高质量配置。

该方向主要是持续优化，不应在缺少项目内基准时承诺某个固定加速倍数。

## 13. 横向治理能力

这些能力不一定单独形成版本功能，但应在对应方向进入时同步设计：

- **成本治理**：调用预算、模型成本估算、超限停止和缓存命中率。
- **运行可观测性**：阶段耗时、错误码、重试次数、证据数量和输入输出摘要。
- **数据安全**：API key、cookie、临时 URL 和用户绝对路径不进入 manifest 或日志。
- **合规边界**：不处理付费、验证码、地区限制或其他访问控制内容，不绕过平台限制。
- **版本和可复现性**：记录模型、提示词、第三方版本和评分规则版本。
- **人工复核**：让人工能从 Skill 结论跳转到时间戳证据，并可记录修改原因。

## 14. 推荐路线

### v0.2：质量可测、失败可恢复、成本可比较

- 分层 Judge 和低成本初筛。
- 蒸馏协议修复、重试、脱敏审计和正确退出码。
- 人工标注集与 Judge 校准。
- ASR 驱动的自适应截图实验。
- 本地 OCR/帧筛选 A/B 实验。
- 有限规模、顺序优先的批处理原型。

### v0.3：多视频证据管线

- 跨视频证据合并。
- Skill 候选去重和版本管理。
- YouTube 单视频适配。
- 更完整的批量调度、预算和汇总。

### v0.3 之后：Search -> Generate

- 自动搜索候选视频。
- 视频证据索引和时间片检索。
- 跨视频问答、冲突分析和引用式 Skill 生成。

## 15. 统一验收原则

未来 Feature 必须至少回答以下问题后才能进入实现：

1. 它解决的是当前已观测问题，还是只增加覆盖面？
2. 它需要改动哪些 manifest、RunState 或管线阶段？
3. 失败时是否可以重跑、隔离和审计？
4. 是否有不依赖真实 API key 的离线测试？
5. 是否有同一输入下的成本、耗时或质量基线？
6. 是否会扩大平台权限、版权或第三方许可证风险？

任何涉及网络、模型或真实视频的结论，都应区分“上游项目声明”和“本项目实测结果”。
